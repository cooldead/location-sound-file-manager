# Location Sound File Manager: notes for working on this project

A PySide6 (Qt 6) desktop app for Linux (CachyOS, KDE Plasma, Wayland), also built for macOS (`macos/build_app.sh`). It manages a library of production sound WAV/BWF files: scanning, grouping by project, playback with a waveform, renaming, metadata editing and reorganising into folders. The user's library is on a CIFS/SMB NAS share with about 21,000 WAVs (2 TB).

For the history of how and why things were built, see `docs/DEVELOPMENT_LOG.md`. For features, see `README.md`.

## Run and test

```sh
./run.sh [library]         # the app  (./install.sh adds it to the app menu)
python3 -m unittest        # unit tests (tests/), no GUI or network needed
```
- **System packages:** `pyside6 qt6-multimedia qt6-multimedia-ffmpeg python-numpy`.
- **GUI testing:** use throwaway scripts that drive `MainWindow` directly, with `XDG_CONFIG_HOME`, `XDG_CACHE_HOME` and `XDG_DATA_HOME` pointing at a scratch dir so the real settings, cache and history stay untouched. Symlink `~/.config/kdeglobals` into the scratch config dir, or Breeze paints the toolbar with light header colours (a test artifact, not a bug). To stay silent while playing, set `window.player.mixer_panel.state.master_mute = True` (the engine still runs and the channel meters still move). `QT_QPA_PLATFORM=offscreen` works (the player needs no GL; audio still goes to the default device).
- **macOS:** `macos/build_app.sh [--install]` makes a venv (`.venv`) and a PyInstaller `.app` in `dist/`. Qt on macOS ignores the `XDG_*` variables (and `$HOME` for its standard paths), so GUI test scripts call `QStandardPaths.setTestModeEnabled(True)` before anything else (paths go to `~/.qttest/`). `settings.open_settings()` follows that on macOS.
- **Windows:** `windows\build_app.ps1 [-Install]` makes a venv (`.venv`) and a PyInstaller folder app + zip in `dist\`; `run.bat` runs from source. GUI test scripts call `QStandardPaths.setTestModeEnabled(True)` as on macOS (`open_settings()` follows it on Windows too; paths go to `%LOCALAPPDATA%\qttest\`). Offscreen Qt on Windows has no fonts unless `QT_QPA_FONTDIR` points at `C:\Windows\Fonts` (`tests/__init__.py` sets it).
- **Never test writes on the real library.** Copy files into a scratch folder first.

## Design decisions (don't undo without a reason)

- **The user approves every change** (a standing preference). Previews for batch renames and moves, a per-field "Change" tick for multi-file metadata, and an explicit prompt, with sizes, before any full-file rewrite. Nothing autoplays.
- **Metadata writes:**
  - iXML is the source of truth; the bext description is a 256-byte legacy mirror. Only keys the recorder already wrote there are updated (no new lines are added), and a long NOTE is shortened *in bext only*.
  - In place means: pad the new iXML with spaces to the old chunk size, or absorb a directly following JUNK/PAD chunk. Otherwise `NeedsRewrite` is raised before anything is written.
  - A rewrite goes to `.sfm-tmp-*.wav` in the same folder, uses `copy_file_range` (server-side copy on SMB), fixes the RIFF size or the RF64 ds64 size, verifies the data size, then `os.replace`. Bytes after the last chunk are kept.
  - Every write is re-read and checked (the fmt bytes and data size are unchanged, the values read back).
  - Renaming a file without iXML updates only the bext FILENAME line, if there is one; it doesn't add iXML just for that.
- **Parser tolerance:** it stops at garbage after the last chunk (seen on real files), retries an odd-sized chunk without a pad byte, and marks a data chunk cut short (`truncated`). Truncated files are never written to.
- **Project** = iXML PROJECT; otherwise the first folder below the library that is neither a "container" (SD_1, SD_2, 833 BACK UPS; configurable) nor date-named (`25Y10M27`, `2024-05-17`). Projects are computed at load time, not cached, so a settings change applies without a rescan.
- **Scanning on the NAS:** the first read costs about 39 ms per file (about 14 min for the library); a cached rescan takes about 3 s per 8,500 files. At startup the cache is shown at once, then a rescan runs and merges its results (new rows appended, changed rows replaced, rows gone removed at the end).
- **Waveform I/O on SMB:** sequential reads run at about 130 MB/s, a random read costs about 8 ms. Files up to 256 MB are read fully in 8 MB pieces; larger ones are sampled (480 × 64 KB, coarse to fine). Both paths emit partial results. Use buffered reads: CIFS returns short reads (rsize 4 MB), which misaligned frames with `buffering=0`. Levels are cached as uint8 peak + RMS per channel (blob starts with `waveform.MAGIC`; older peaks-only blobs are treated as missing).
- **Playback is our own engine, not mpv** (since the mixer): mpv could not change per-channel gains live or give per-channel meters. A reader thread `pread`s and decodes ~1.4 s ahead (never blocking the GUI on the NAS); the GUI thread mixes 512-frame pieces through `MixerState.matrix(frame)` (ramped between pieces so moves don't click) into a `QAudioSink` kept ~0.2 s full, so mixer changes are heard within that. Every piece is recorded with its file frame and meter peaks; `processedUSecs()` maps back to the frame being heard (playhead, meters, loop wraps). Pause = stop the sink and re-read from the playhead. Qt 6.8+ renamed the `QAudio` enums to `QtAudio`: compare `error().name` / `state().name`, not enum values.
- **Mixer:** poly files have no speaker layout: every track is panned centre with a constant-power law scaled to unity at centre; the mix is lowered by 1/√n for n playing tracks (`auto_trim`) so correlated mics don't clip. Mute beats solo. Automation is written while a track is armed and playing (each tick overwrites the stretch since the last), and plays back otherwise; tracks are disarmed when another file loads.
- **The player releases the file** (`engine.close()`) before a rename or write that affects it, then reloads at the same position (paused). SMB may refuse to change open files.
- **Take families** (Sound Devices `_ISO` + `_LR`) share the iXML FAMILY_UID in the same folder; metadata edits offer to include them.
- **Moves** only move audio files. "Remove folders left empty" treats `.take_folder`, `.daily_folder` and `.DS_Store` as empty and deletes them, including subfolders that hold only those (`organize.empty_tree`; before, a leftover `day/.daily_folder` kept its parent alive). *Delete Empty Folders* scans the whole library (`find_empty_folders`, ~7 s on the NAS) and re-checks each folder right before deleting it. Undo recreates the folders and the empty markers (not `.DS_Store`).

- **Offload never writes to the card.** Review edits are pending in `RecordingsModel.pending` (path → changes) and written into the NAS copies after verification. The copy then gets the card file's mtime back (`_keep_card_dates`), so a later offload of the same card sees it as "same" (size + mtime within 2 s). Renames already written are remembered for the session (`done_names`).
- **The copy layout** is `<library>/<NAS folder name>/<path below the card's project folder>`, which matches the existing library (833: `<Project>/<YYMMDD day>/[take folder/]`). The NAS folder name defaults to the card folder name and is remembered per card folder name.
- **Projects already in the library** (offload): after a card is read, `duplicates.card_project_matches` compares each card folder (its name and its files' iXML projects) with `project_locations` of the library, using the Find Duplicates rules (`normalize`, `similar_names`). A match whose folder isn't already the copy's target (and is below the destination) goes into `ExistingProjectsDialog`: merge (sets the NAS folder name to the existing folder, relative, remembered like a typed name), new folder, or skip (`skip_folders`, unticked). "Already in the library" is `recording_key` (name + `audio_key`), no reads. Days whose new audio is all in the library elsewhere are not ticked by default. The Library may load after the card was read (startup): `library_ready()` runs the check then and resets the default ticks.
- **Card switching** bumps a plan generation, and reader results are checked against the current card, because late results for the previous card used to arrive after the switch.
- **Library actions are disabled on the Offload page** so their shortcuts (F2, Ctrl+E…) go to the review table.
- **Waveform drawing:** rendered once into a pixmap by numpy rasterisation with anti-aliased coverage (about 45 ms overlay / 15 ms lanes at 1600×300 for 6 channels; Python polygons took 77 ms for the old one-colour version). Regions, markers and the playhead are painted on top, so they never re-render it. The overview has 4096 buckets (sharp at full width on most screens); when zoomed past that, `WaveformView` emits `detailWanted` and a `_DetailJob` reads just the visible frames at one bucket per device pixel (`compute_peaks(first_frame, end_frame)`), shown only if the view hasn't changed meanwhile. Peaks are drawn in the full track colour and the RMS body lighter, with one-pixel anti-aliasing (a half-tone outline looked blurry). It re-renders only when the set of audible tracks changes, not on every fader step. Playhead moves repaint only two 5-px strips. Files over 48 MB get a coarse preview (48 blocks) before the full read. The next 3 rows are prefetched into the peaks cache at low priority and cancelled when the selection changes.
- **iXML with a stale tail:** the 833 rewrites iXML in place and can leave the end of a longer, older document after a NUL. The parser cuts at the first NUL / `</BWFXML>`. Cache `PARSER_VERSION` 2 re-reads only the entries without iXML.
- **Reports are grouped by project**: in the Library by the recordings' project (from the sidebar multi-selection, the selected rows, or the current scope), and in Offload by card project folder. Offload writes one report per project into `<library>/<NAS folder>/` by default, or per card day folder (`report_per`), grouped by card folder and day, never by each file's own folder (833 take folders would give a report per take).
- **32-bit float WAVs** (format 3, plain or WAVE_FORMAT_EXTENSIBLE; 64-bit too) are decoded everywhere (`waveform.decode`); NaN/infinity in a damaged file become 0/±1 there. Float files can hold peaks above 0 dBFS: levels are capped at full scale, and `rasterize` marks full-scale columns red at the lane's top and bottom (`OVER_LEVEL`, from the nearest bucket when stretched). The mix output is clipped to ±1 but the meters show the over, so the fader can bring it down. Real case: a Deity PR-2 backup recorder (mono, +0.7 dBFS peaks). Tests: `tests/test_float.py` (`make_wav(float_samples=…)`).
- **Offload "same audio":** a destination file with the same name but a different size or date is fingerprinted (`duplicates.sample_hash`) by the `Planner`; the same audio means status "same audio" (`CopyItem.on_nas`), shown as on the NAS, not a conflict. Real case: 833 copies 12 bytes shorter or longer on the NAS after later metadata writes. Recorder marker files (`.daily_folder`…) don't make a day "new" (merges and empty-folder cleanup remove them from the NAS, which used to tick days that were fully backed up).
- **Editing in the Library table:** `RecordingsModel(live_edit=True)` makes File/Scene/Take/Note editable (double-click) but writes nothing itself: `setData` emits `editRequested`, and `MainWindow.apply_cell_edit` writes at once through `do_metadata` / `do_renames` (★ double-click and the notes box use the same path). The take's partners (`catalog.family_members`, when `apply_to_take_family`) get the same change. Scene/take edits rename to `renamer.scene_take_name` (keeps the recorder's separator and `_ISO`/`_LR`/`_1` endings; scene+take found inside a longer name, at a word boundary and not followed by a digit, is replaced in place so `2BT001_BOOM` → `2BT002_BOOM`; `<scene>T<take>` otherwise; nothing until both are set) when `rename_on_scene_take`; a File rename takes partners along via `partner_name`. New names are checked (valid, free) before anything is written; metadata + rename is one compound undo step (`do_renames(push_undo=False)` returns its part). Full rewrites leave `REWRITE_IXML_HEADROOM` (4 KB) of spaces after the iXML so the next edits fit in place (a file without metadata used to need a full copy for every later edit).
- **Split into track files** (`splitter.py`, `MainWindow.split_selected`, `dialogs.SplitDialog`): one mono file per track named after the track (safe_part; repeats get `_2`, unnamed `Track N`) in `<folder>/<name without _ISO/_LR ending>/`. Each keeps the bext (description cut to its own `TRK1`, FILENAME updated) and the iXML (TRACK_LIST cut to its track with INTERLEAVE_INDEX 1, same FAMILY_UID, TOTAL_FILES / FILE_SET_INDEX, new FILE_UID, HISTORY PARENT_FILENAME/PARENT_UID) plus `cue `/`LIST`; RF64 when over 4 GB. Written in one read pass under `.<name>.part`, checked, then renamed; any failure removes them. The take's partners (`family_members`) move in with it (_ISO/_LR stay together). Tracks are chosen per file (`plan_split(picked=…)`); the unticked ones stay with the original: it moves in whole (`originals_in_folder`, whatever `split_keep_original` says, since it holds them), or with `shrink` (`split_shrink_original`) a `remainders` file with those tracks (`TrackFile.channels`, renumbered TRK/INTERLEAVE_INDEX) is written under the original's name in the take folder, in the same read pass, and the full file goes to the removed folder. With every track split off, the original moves in (`split_keep_original`) or to the removed folder. Ticked tracks can be grouped into one polywav (`plan_split(groups={path: [(name, channels)]})`, a `TrackFile` with `channels`; default name joins the track names with "+"). `is_track_file` also covers group files: a file in a folder named after its `original_filename`'s take whose name neither starts with that take nor contains its scene and take. Undo is a compound step: rename part (moves back), then a "copies" part (deletes the track files, `created_dirs` removes the new folder). Scene/take edits skip `is_track_file` files (they would otherwise be renamed `<scene>T<take>`).
- **Combine into polywav** (`splitter.combine_problems` / `combined_name` / `combine_files`, `dialogs.CombineDialog`, `MainWindow.combine_selected`): the files must line up (same frames, rate, bits, int/float, time reference). One pass reads a block from each source and `np.concatenate`s along the channel axis. The first file's bext (TRK lines rewritten for all tracks only if it had any and they fit) and iXML (TRACK_LIST = every source's TRACK nodes in order, INTERLEAVE_INDEX renumbered, new FILE_UID, CURRENT_FILENAME) are used. Default name (`combined_name`): scene + take in the style of the files' `original_filename` take core if it is built from them, else `<scene>T<take>`, plus `_<file stems joined by +>` when taken. Undo: a "copies" part for the new file, plus a rename part when the sources went to the removed folder.
- **Permanent delete in split / combine** (`split_delete_permanently`, `combine_sources` = keep/remove/delete; `dialogs.confirm_permanent_delete`): files are deleted (`main_window._delete_files`) only after the new files are written, checked and the moves done. No undo step is pushed then (undoing would delete the new files, now the only copy), and `_forget_undo_for` drops older steps that need the deleted files. `safety_mode` (Settings, default "safe"): safe never preselects a permanent delete (falls back to the removed folder) and always confirms; "dangerous" preselects the remembered choice and skips `confirm_permanent_delete` (`dialogs.dangerous_mode`, a red `dangerous_label` in both windows).
- **QMessageBox.setCheckBox needs a Python reference to the checkbox:** PySide doesn't take ownership, so `box.setCheckBox(QCheckBox(...))` deletes the checkbox at once and the box segfaults using it (the Undo crash, in `exec()` on KDE and in `checkBox()` offscreen).
- **Library report windows are non-modal** (`WA_DeleteOnClose`, kept in `_report_windows`), so several can be open at once.
- **PDF:** `documentLayout().setPaintDevice(writer)` is required, otherwise the layout is made at screen DPI and the text comes out tiny.

- **Tests and Qt:** always use `tests.qt_app()` (one `QApplication`); a bare `QGuiApplication` from one test module later used for widgets corrupts the heap. Dialogs sit in reference cycles, so tests delete them with `tests.dispose()`, and `__main__` frees the window before interpreter exit.

- **Duplicates:** removal always re-checks byte for byte right before removing: `level` is "identical" (whole file) or "audio" (fmt + data; the 833's second-card copy can differ in layout). Removed files go to `<library>/_Removed Duplicates/<original project>/<original path>` (`catalog.REMOVED_FOLDER`, which the scanner skips), so undo is a rename. Merges skip twins whose metadata differs (the user picks in the Files tab). A merge can target a new folder: files are planned best copy first (`keeper_score`), and a planned move counts as "kept", so its twins become removals, verified against the moving file's current path before anything moves. FALSETAKES, TRASH and Recovered are never project locations.
- **Review copies:** `Cleanup.review_mode` is "copy" (default), "move" or "skip". With copy or move, only byte-identical files are removed; anything else goes next to the kept copy (at its final place after moves) as `<name>_ReviewForDeletion<ext>`. Copies use `offload.copy_items` (verified) and are undone by deleting them (the "copies" undo part). Merge twins whose metadata differs are the "differs" action kind. Deleting for good drops the undo steps that need those files (`_forget_undo_for`).
- **_ISO/_LR takes are one unit** (the user's standing rule): `is_take_file`. They never get review copies and are never renamed. In a merge, a same-named twin is removed whatever its notes say (level "audio"), and a differently named twin is moved in. `keep_takes_together` turns move/remove into skip for the partners of a take file that stays. At removal, `make_cleanup_work` skips an _ISO/_LR file whose partner in the same folder isn't also leaving. `keeper_score` prefers a copy with a note, so notes aren't lost.
- **Versions with more tracks are preferred** (merges): a name clash in the kept folder where `more_tracks_candidate` holds (same name/frames/rate/bits/timecode, different channel count). The larger file replaces the smaller (level "subset"), or the smaller incoming file is removed (level "subset"). `channels_contained(small, big)` verifies over the whole data that every small channel equals some big channel byte for byte (numpy, 8 MB blocks). Real case: Zoom F8 copies with and without TrL/TrR. `Cleanup.replacements` are 3-tuples `(rec, old, level)`.
- **Versions with notes are preferred:** `adds_notes(better, base)` means the same name and metadata, except a note or circle the base lacks. In merges it becomes a "replace" action (`other` = the replaced copy; if the twin was itself a planned move, the noted copy moves instead). In Duplicate Files it's `FileGroup.replacement`. `Cleanup.replacements` is executed after an audio check as two ops in the same rename batch: the old copy goes to the holding folder and the noted copy moves to the old path (undoable). _ISO/_LR partner rules still apply.
- **Compare marked files:** `pair_review_copies` (same name in the same folder, else the same audio_key elsewhere) and `compare_rows`. The swap is `MainWindow.keep_marked_copy`: the kept file goes to the holding folder and the marked copy takes its name (undoable).
- **Batch merge** (`BatchMergeDialog`): plans every checked group up front for display, then runs them one after another. Each group is re-planned from the current library (`refresh_group`) right before it runs, because an earlier group may have moved files. The file work runs in a `_BatchWorker` through `MainWindow.make_cleanup_work(plan, known_paths)`; `finish_cleanup` updates the library after each group. At the end come one compound undo step (`cleanups_done`) and one report of failures. A single merge uses the same `make_cleanup_work` / `finish_cleanup` / `write_rewrites` / `cleanups_done`.
- **Nested folders** (`find_nested_folders`, `plan_nested_merge`, the third Find Duplicates tab): a folder whose parent has the same `normalize`d name, below a library folder. `plan_project_merge` can't do it (the inner folder is inside the kept folder, so every file counts as already there), so the plan maps each inner file to the same path one level up: move, remove (the same recording there; byte check at removal), replace (notes), differs, or skip (another file in the way); `keep_takes_together` applies. The result is an ordinary `Cleanup` (one undo step, also for several). Only the deepest of A/A/A is listed. Test WAVs from `wavmaker` all share FAMILY_UID `FAM1`, so they count as one take; give each take its own id when testing take rules.
- **Fingerprint reads in parallel:** `FINGERPRINT_WORKERS` = 4 (Wi-Fi to the NAS: 86 ms per file serially, 57 ms with 4, no better with more). `plan_project_merge` prefetches the fingerprints its loop will ask for.
- **Fewer fingerprints:** copies with the same audio_key and the same file name are taken as the same recording without reading them; a fingerprint is only read for one file per distinct name in a group (e.g. _ISO vs _LR, renamed copies). This is safe because every removal is re-checked byte for byte. It cut a first scan from 11,725 to 3,880 files on the real library. Merge plans use the same shortcut.
- **Project finding is string work:** `_relative_parts`, and `_FolderIndex` (the files below each folder) instead of pathlib and per-group scans over all recordings. It went from 98 s (29 s without the profiler) to 0.37 s with identical results. After a merge the window re-runs it automatically.
- **Fingerprints on the NAS:** unbuffered `pread` with `POSIX_FADV_RANDOM` (macOS: `F_RDAHEAD` off) and 64 KB samples. Buffered reads pulled the 4 MB CIFS read-ahead per sample (99 → ~50 ms per file). Parallel reads measured no faster wired on Linux, but help over Wi-Fi (see above).

- **Library index:** measured over Wi-Fi to the NAS (12 ms ping): a first scan costs ~130 ms per file (open/close alone ~60 ms), the walk ~32 ms per folder + ~8 ms per WAV. The index removes the per-file reads, not the walk. Four settings: `library_index_read` / `library_index` (use / update file metadata) and `library_index_waveforms_read` / `library_index_waveforms` (use / update waveforms). Use is on by default (it changes nothing), update is off (the user approves changes to the library). Metadata is written by `ScanThread` only after a complete scan and only when something changed; ticking waveform update shows a storage warning (estimate + free space); they are written by `_PeaksJob` as files are first drawn (and prefetched), only for files below the library. No SQLite on the share: two computers writing one database over SMB can corrupt it, while whole-file replaces can't. Entries match with an mtime tolerance of 10 ms (the same SMB timestamp read by two clients).
- **Parallel walk:** `catalog.walk_audio` lists folders and stats files with `WALK_WORKERS` (16) threads, because each request waits on the network: Wi-Fi to the NAS, 16,700 files took 273 s serially and ~70 s in parallel (32 or 64 were no faster). The order of results is not fixed. A folder that can't be listed goes into `ScanStats.unlisted`; then nothing is pruned, the index isn't rewritten and the window keeps those rows (before, a Wi-Fi drop made files "gone", and the next scan read them all again).
- **Platform differences** stay small and in place (`sys.platform == "darwin"`): card detection (`/sbin/mount` for local `/dev/` mounts, so a network share is never touched by the 3 s poll, then `diskutil info -plist`, cached per device; `RemovableMedia` or an SD bus counts as a card), eject (`diskutil eject` of the whole disk), `MEDIA_FOLDER`, settings in `~/Library/Application Support`, `REPORT_FONT`. macOS has no `copy_file_range` (rewrites copy through a buffer) and no `posix_fadvise` (fingerprints turn read-ahead off with `F_RDAHEAD`). Shortcut text shown in the UI goes through `main_window.keys()` (⌘ on a Mac), and "Ctrl-click" in hints through `dialogs.MULTI_CLICK`. On macOS a click makes any tree row current, also rows without a group (a group's folder rows): `DuplicatesWindow._selected_group` walks up to the group, a folder row picks that keep folder, and the first group is selected after a search. Mac disks and the SMB share ignore case, so a typed new folder that exists under another case is planned with its spelling on disk (`_existing_spelling`). For the same reason `card_safety` compares paths casefolded and NFC on macOS (realpath keeps the given spelling there), so a card path in another case is still protected. `macos/build_app.sh` needs Rust (`brew install rust`) for `scripts/build_native.py`; the `.dylib` is bundled with `--add-binary` (about 4× faster reductions than numpy on Apple silicon: 13.6 vs 57.4 ms per minute of 6-track 24-bit).

- **Windows** (`compat.py`, `win_drives.py`): paths inside the app always use "/" (Windows accepts it, and Qt's dialogs return it), because so much here is string work on "/" and the library index keys must match other computers. So use `compat.join` / `compat.normpath` / `compat.relpath` instead of `os.path`'s, and `compat.fwd()` on anything from `os.scandir`/`os.walk`, `str(Path)` or `os.path.commonpath`; folder settings are read back through `compat.fwd` (`settings.PATH_KEYS`). There is no `os.pread` (`compat.pread` = `ReadFile` at an offset) and low-level `os.open` needs `compat.O_RDONLY` (binary). Cards are drives of type `DRIVE_REMOVABLE` (only the type is asked, so mapped NAS drives are never touched by the poll); eject = lock, dismount and `IOCTL_STORAGE_EJECT_MEDIA`. `renamer.validate_name` refuses names Windows can't hold. Tests: `tests/__init__.py` makes temp folders with "/" like the app.

## Conventions

- Match the existing style: pure logic in modules without Qt, with unit tests. Dialogs are thin. Comments explain *why*.
- The repository is **public**: https://github.com/cooldead/location-sound-file-manager (MIT). Never commit personal details: real client/project names (the tests use made-up ones), NAS addresses or paths, recorder serial numbers, emails or phone numbers. The history was started fresh at v1.0.0 for this reason.
- The desktop file is a template (`@APPDIR@`); `install.sh` fills in the path.
- Releases: `gh release create vX.Y.Z`. Platform builds are separate releases: Linux as `vX.Y.Z-linux` with `Location-Sound-File-Manager-X.Y.Z-linux.tar.gz` (`git archive` of the tag without `macos/`) + `.sha256`; macOS with the `-macOS-arm64.zip` from `macos/build_app.sh`. Update the README's Download table links when either changes. Linux packages: `linux/build_packages.sh X.Y.Z` builds the tarball, the Arch package (`linux/PKGBUILD`, sha256 filled in from the tarball) and an AppImage from the tag's code; upload the tarball and Arch package by hand. The release AppImage comes from `.github/workflows/linux-packages.yml` (Ubuntu 22.04, on publishing a `-linux` release or by `gh workflow run linux-packages.yml -f tag=vX.Y.Z-linux`): one built on CachyOS needs glibc 2.44. **Testing an AppImage here:** the user has AppImageLauncher, which intercepts AppImages and asks on the desktop first; set `APPIMAGELAUNCHER_DISABLE=1` (and never `pkill -f` a pattern that is also in your own command line). The first release was v1.0.0 (2026-09-25); v1.1.0 (2026-09-26) was squashed from local work the same way (the detailed history is on the local `pre-v1.1-history` branch, never pushed).
